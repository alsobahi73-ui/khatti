# تحسين تجربة التسجيل والبحث وأول حجز

حالة التسليم: تحسين تجربة الواجهات الحالية، مع المحافظة على الألوان وRTL ومتطلبات `PROMPT.md`. يعتمد فرع `feat/onboarding-first-booking` على وحدة الحسابات في `feat/server-registration`؛ لا يغيّر هذا العمل حالة النشر أو يفعّل SMS أو حجزًا إنتاجيًا.

## رحلة الاستخدام

| الخطوة | التحسين |
|---|---|
| تسجيل الراكب | بيانات أساسية، ثم رمز، ثم بدء البحث؛ ربط الابن التجريبي اختياري ضمن قسم مطوي |
| تسجيل السائق | بيانات أساسية، رمز، بيانات المركبة، ثم صورة الإجازة وملخص الطلب؛ حالة المراجعة ظاهرة ولا قبول ذاتي في وضع الخادم |
| استكمال المركبة | حفظ مسودة، ومؤشر يميز الحفظ المؤكد والتغييرات غير المحفوظة، وإمكانية المتابعة لاحقًا |
| البحث | فلاتر محافظة/منطقة/جهة/صفة وسعر وتقييم، وعدد نتائج، واستعادة فلاتر التبويب، وزر مسح الفلاتر والدبوس |
| اختيار الخط | إبراز نقطة الالتقاط والذهاب والإياب والسعر اليومي والشهري والمقاعد، مع بقاء وصف الشارات كتجريبي |
| الحجز التجريبي | اختيار نقطة الالتقاط والنوع والدفع، ثم مراجعة الاسم والهاتف والمواعيد والسعر قبل الحفظ؛ تعديل دون فقد المدخلات |
| بعد الحفظ | رسالة نتيجة تبين أنه سجل محلي بلا إرسال أو دفع، وروابط «رحلاتي» والبحث مجددًا؛ تفاصيل الالتقاط والسعر ظاهرة في السجل |
| الأخطاء والاتصال | رسائل داخل النموذج، توجيه التركيز للحقل غير الصالح، وحالة اتصال ظاهرة؛ طلب خادمي بمهلة زمنية ومدخلات باقية عند الفشل |

أرقام الهاتف في الواجهة تقبل الصيغ العراقية المحلية والدولية والأرقام العربية والفارسية والمسافات، وتتحقق من صيغة المحمول. لا يثبت ذلك ملكية الهاتف؛ وضع SMS ما زال اختباريًا.

## أين تُحفظ المسودة؟

- **الخادم:** migration `002-driver-drafts.sql` تضيف `driver_drafts`. المسودة مرتبطة بهوية الجلسة في الخادم وتحتوي نوع المركبة واللوحة والسنة والمقاعد فقط. لا اسم/هاتف إضافيين أو رمز OTP أو صورة في مسودة المتصفح. المسودة لا تمنح صلاحية ولا تغيّر قرار التوثيق.
- `GET /v1/driver/draft` يعيد مسودة السائق الحالي فقط، و`PUT` يحفظ الحقول المسموحة مع CSRF وOrigin ودور السائق. الحقول الجزئية مسموحة للمسودة؛ الإرسال النهائي يتحقق من القيم كاملة.
- الحفظ التلقائي بعد توقف الكتابة بنصف ثانية، وزر «حفظ والمتابعة لاحقًا» ينتظر تأكيد الخادم. عند انقطاع الاتصال تبقى المدخلات في الصفحة وتُعاد محاولة حفظ المسودة عند عودة الاتصال؛ لا تدّعي الواجهة تأكيد حفظ لم تتلقّه. إغلاق الصفحة قبل التأكيد قد يفقد آخر تعديل.
- عند نجاح تقديم طلب المراجعة، تحذف المسودة في معاملة حفظ الطلب نفسه. الصورة ترفع فقط عند الإرسال، ولا تحفظ كمسودة. إعادة محاولة الإرسال من الشاشة نفسها تعيد استعمال معرف الصورة المرفوعة بدل تكرار رفعها؛ بعد إعادة فتح الصفحة يلزم اختيار الصورة مجددًا.
- **العرض الثابت:** تحفظ مسودة المركبة التجريبية محليًا تحت `khatti_demo_v1_registration_vehicle_draft` دون صورة أو OTP. إعادة الفتح تتطلب تكرار محاكاة الرمز قبل استرجاع المركبة؛ لا تُحفظ جلسة تحقق مزعومة. تظل بيانات العرض غير صالحة للعملاء الحقيقيين.

تدعم أداة migrations الآن الملفات المرقمة بترتيبها، وتسجل كل migration داخل معاملة. تختبر ترقية قاعدة الحسابات السابقة واستمرار البيانات بعد إعادة التشغيل، دون حذف الحسابات.

## الحجز والتعامل مع الفشل

زر المراجعة لا يضيف حجزًا. الحفظ يتم فقط عند التأكيد الأخير؛ يعاد فحص السعة وتمنع النقرات المتكررة، ويحفظ سجل الحجز والرحلة معًا. عند فشل التخزين تبقى شاشة المراجعة متاحة لإعادة المحاولة ويظهر الفشل. تظل السعة محلية ولا تمثل سعة مشتركة بين الأجهزة؛ منع تضارب حجوزات متعددة الأجهزة يحتاج API الحجز المخطط له لاحقًا.

الفلاتر تحفظ في `sessionStorage` للتبويب نفسه، دون إحداثيات دبوس المنزل. لا يُدّعى تشغيل PWA بلا اتصال؛ تحميل الصفحة نفسها أول مرة والخرائط يحتاجان توفر الملفات والاتصال المناسب. عند تعذر الخرائط تبقى الفلاتر والقائمة متاحتين متى كانت الصفحة محمّلة.

في وضع الخادم تبقى صفحات الحجز والتتبع والدفع غير المربوطة محجوبة، ولا تُستخدم الحسابات الخادمية لإنتاج حجز محلي يوحي بخدمة حقيقية. لتحسين رحلة الحجز كاملة اختبر العرض الثابت؛ وللحسابات ومسودة السائق شغل `npm run dev:server` وفق [دليل الخادم](SERVER-REGISTRATION.md).

## الاختبارات والتحقق

تغطي الاختبارات تدفق راكب جديد حتى أول حجز تجريبي دون إنشاء بيانات مسبقة، وتعديل الحجز قبل الحفظ، ومنع التأكيد المتكرر، وإعادة فحص المقاعد بعد المراجعة، وجمع فلاتر السعر والتقييم واستعادتها، واسترجاع مسودة السائق في الوضعين، والصلاحيات وCSRF، وبقاء المدخلات عند تعذر الرمز وانقطاع الاتصال واستئناف حفظ المسودة.

كشفت اختبارات التنقل أن حد الطلبات العام كان يحتسب ملفات الواجهة؛ أصبح الحد خاصًا بمسارات API حتى لا يمنع تحميل الشاشات أثناء التنقل. بقي حد OTP حسب IP وحدود الهاتف/المحاولات في الخادم، وأضيف اختبار يؤكد ذلك. أضيف أيضًا اختبار حذف المسودة بعد تقديم الطلب.

شغّل `npm test` للتحقق من TypeScript والحزمة والروابط والمنطق وAPI والواجهات. الشاشات روجعت بصريًا بعرض 390 بكسل، دون تغيير قيم ألوان الهوية أو إعادة بناء المشروع. لا اختبارات نشر/أجهزة فعلية أو SMS حية ضمن هذا العمل.

## حدود المرحلة التالية

لا خدمات مدفوعة أو قاعدة إنتاجية جديدة، ولا تغيّر لنطاق المشروع. يلزم لاحقًا ربط البحث والحجز بالخادم ومعاملات السعة، واختيار SMS وتفعيلها في بيئة ملائمة، ثم اختبار أجهزة Android وiOS. التحقق الميداني ومتطلبات الإطلاق في قسم 6 من `PROMPT.md` مستمران؛ تحسين التجربة لا يثبت نجاحهما.

## نتيجة التحقق المسجلة

نجح فحص TypeScript وتشغيل مجموعة `npm test` كاملة، ثم نجح اختبار ترقية قاعدة 001 بصورة مستقلة: 7 اختبارات للمنطق والحزمة، و17 سيناريو API بالإضافة إلى اختبار ترقية مستقل، و16 اختبار متصفح للعرض و4 اختبارات متصفح للخادم. لا حالات فشل أو تخطٍ في الجولات النهائية. يعرض مشغّل Node مجموعة سيناريوهات API أيضًا كحالة إضافية، لذلك يظهر عدد 19 في جولة الخادم التي تتضمن اختبار الترقية.

لم تتغير الاعتماديات أو `PROMPT.md`، ولم تتغير قيم ألوان CSS الأساسية. الملفات المعدلة تشمل وحدات الواجهة المشتركة والتسجيل والبحث والحجز، وإضافة تحميل وحدة الرحلة إلى الصفحات، وAPI ومخطط مسودة السائق، والاختبارات وهذا التوثيق.
