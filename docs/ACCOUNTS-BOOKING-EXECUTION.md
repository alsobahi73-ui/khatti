# خطة تنفيذ الحسابات والحجوزات الحقيقية — خَطّي

التاريخ: 15 تشرين الأول 2026. الحالة: مراجعة للكود وخطة تنفيذ، وليست إطلاقًا لخدمة إنتاجية.
المرجع الأساسي: [PROMPT.md](../PROMPT.md)، خصوصًا التسجيل 3.12، الخصوصية 5، والإطلاق 6. تبقى الهوية العربية وRTL والألوان والواجهات الحالية. لا إعادة بناء من الصفر ولا واجهة مؤسسات.

## القرار المقترح

نبدأ باستعادة وحدة الحسابات الموجودة في فرع التطوير ودمجها تدريجيًا، ثم نضيف الحجز والمقاعد في بيئة اختبار ببيانات اصطناعية. نختار جامعة واحدة وخطًا واحدًا مع 2–3 سائقين للتجربة، والكاش أولًا. لا شراء استضافة أو SMS ولا استقبال وثائق عملاء حقيقية ضمن هذه المهمة.

نجاح التحقق الميداني لشهر و50 مشتركًا دافعًا غير مثبت في المستودع؛ لا نفترض تحققه. يمكن إعداد واختبار الخدمات محليًا بالتوازي، لكن إطلاق التجربة للعملاء يحتاج نتيجة التحقق وقرارات التشغيل أدناه. التطبيق لا يستقطب سائقين أو يتواصل معهم تلقائيًا.

## نتيجة مراجعة الموجود

لقطة أساس المراجعة: `main` عند `0f4b763`؛ فُحصت الملفات والفروع المحلية، ولا يعني وجود فرع أن محتواه منشور أو صالح للإنتاج.

| الجزء | الموجود | القرار |
|---|---|---|
| الويب الحالي | HTML/CSS/JavaScript وCapacitor؛ حفظ الحساب والحجز في localStorage | الحفاظ على الواجهات وربطها تدريجيًا بـAPI؛ التخزين المحلي ليس مصدر الحقيقة |
| التغليف والاختبارات | آخر تحديث 0f4b763 أعاد register.html وأوامر npm test | الاعتماد عليه؛ لا إعادة تنفيذ الإصلاح |
| الحسابات الخادمية | `feat/server-registration` عند 43391d2: Fastify/TypeScript، جلسات، OTP اختبار، وثائق خاصة ومراجعة سائق | إعادة استخدام بعد مراجعة الفروق واختبارات جديدة؛ ليس ضمن main |
| قاعدة تطوير | PGlite على القرص مع موصل PostgreSQL خارجي مكتوب | PGlite للتطوير فقط؛ اختبار migrations والتزامن على PostgreSQL حقيقي قبل الإنتاج |
| SMS | واجهة SmsSender وصندوق اختبار محلي | لا رسالة حقيقية ولا إثبات ملكية هاتف؛ يلزم موصل مزود واختبار العراق |
| الحجز | منطق محلي في passenger/booking.html؛ لا معاملات مشتركة | تنفيذ خدمة جديدة فوق الحسابات الموجودة |
| بحث بنقطتي الخريطة | `feat/map-trip-search` عند d5b4b39؛ ليس من أسلاف main في المراجعة | دمج مستقل بعد مراجعة؛ لا ربط الحسابات الحقيقية ببياناته التجريبية |
| التتبع | صفحة live-tracking ضمن main، محاكاة وموقع هاتف محلي | إبقاء توضيح المحاكاة؛ لا اعتباره تتبعًا بين الأجهزة |
| خطط سابقة | `docs/real-mvp-plan` وdocs في فرع الحسابات | مراجع سابقة؛ هذه الوثيقة تحدث الحالة ولا تدعي إعادة تنفيذها |

لا تدمج فرع الحسابات كاملًا دون مراجعة: يغير التسجيل وruntime وapp.js والتغليف والاعتماديات، وقد يعيد صفحات أقدم. دمج الوحدات على أحدث main مع الحفاظ على المحافظات الـ19 وصفحة التتبع وتصميم الصفحة الرئيسية. يُعاد تقييم الاعتماديات والقفل وقت الدمج؛ لا ننسخ node_modules.

## البنية المستهدفة

المتصفح/Capacitor ← HTTPS API ← PostgreSQL. صور الوثائق في تخزين خاص منفصل، وSMS من الخادم فقط. خادم API يخدم الويب من الأصل نفسه في أول تجربة لتبسيط الجلسات. GitHub يبقى للكود وCI؛ GitHub Pages يستضيف العرض التجريبي ولا يشغل قاعدة البيانات أو Fastify.

- إعادة استخدام server/app.ts وdb.ts وsecurity.ts وsms.ts وmigrations في فرع الحسابات، مع فصل وحدتي الخطوط والحجوزات بدل تضخم ملف واحد.
- جلسة ويب HttpOnly وSecure وSameSite مع حماية CSRF وتحقق Origin، وصلاحيات خادمية لكل عملية. لا رموز جلسات في localStorage ولا اعتماد role من العميل.
- لا يُفتح وضع production بتعطيل الحاجز الموجود فقط؛ يُفتح بعد تنفيذ SMS الحي والبنية والقبول الأمني والاستعادة.
- بيانات العرض التجريبي منفصلة بوضوح عن وضع الخادم. لا ترحيل تلقائي لحسابات أو حجوزات localStorage؛ العميل يستطيع تعديلها ولا تصلح دليل ملكية أو دفع.
- يختبر Capacitor عبر HTTPS واختيار آلية جلسات مناسبة على Android/iOS قبل اعتماده. لا نفترض أن cookies الويب تعمل دون تعديل داخل WebView.

## نموذج البيانات المقترح

نحتفظ بجداول users وuser_roles وauth_challenges وsessions وdriver_profiles وdriver_documents وaudit_events الموجودة، ثم نضيف migrations مرقمة:

| الكيان | الحقول والقيود الأساسية |
|---|---|
| lines | driver_id، نقاط انطلاق/وجهة ومسار، مؤسسة، صفة الخط، الأسعار بالدينار كأعداد صحيحة، status؛ لا نشر قبل موافقة السائق |
| trips | line_id، وقت انطلاق/عودة محدد وtimezone بغداد، capacity، status؛ لكل رحلة صف مستقل |
| subscriptions | passenger_id، line_id، بداية/نهاية، نوع وأيام الاشتراك، status؛ لا تمديد تلقائي غير مصرح |
| bookings | passenger_id، trip_id، subscription_id اختياري، seats، pending/confirmed/rejected/cancelled/completed، سبب/تاريخ القرار، idempotency_key |
| cash_records | booking/subscription، المبلغ، unpaid/received، السائق المؤكد، وقت التأكيد؛ موافقة الحجز لا تعني استلام النقد |

تأكيد الاشتراك الشهري يحجز مقعدًا في كل الرحلات المجدولة ضمن فترة محددة مسبقًا، وليس في تاريخ مفتوح. الاشتراك pending لا يضمن مقعدًا. إذا تعذرت أي رحلة مطلوبة يفشل التأكيد كله ويعرض التعارض؛ لا تأكيد جزئي صامت. تغيير الجدول أو سعة المركبة يفحص الحجوزات المؤكدة أولًا. طلب حجز يومي لرحلة مغطاة باشتراك قائم يُرفض كتكرار.

## منع تجاوز المقاعد وتكرار العمليات

1. طلب الراكب ينشئ pending بمعرف طلب ثابت؛ إعادة المحاولة بعد انقطاع الإنترنت تعيد النتيجة نفسها.
2. موافقة السائق تتحقق من ملكيته للخط، وحالة توثيقه والطلب، ووقت الرحلة.
3. داخل معاملة PostgreSQL تُقفل صفوف الرحلات بـSELECT FOR UPDATE بترتيب معرف ثابت، ثم تُحسب المقاعد المؤكدة ويُتحقق من السعة.
4. تُؤكد جميع حجوزات الفترة أو تُلغى المعاملة كلها. قيد فريد يمنع تكرار حجز الراكب للرحلة حسب السياسة. لا نعتمد تحقق واجهة المستخدم لمنع التزاحم.
5. الإلغاء يغير الحالة مرة واحدة داخل معاملة ويحرر المقاعد؛ لا حذف سجل القرار. رفض الطلب لا يسحب مقاعد لأنه لم يحجزها أصلًا.
6. لا صف انتظار تلقائي ولا تأكيد دفع إلكتروني في هذه الدفعة. عند عدم الاتصال يظهر «لم يُؤكد بعد»، ويُستعلم عن النتيجة قبل تكرار العملية.

## عقود API المقترحة

مسارات auth وme ورفع الوثائق والمراجعة موجودة في فرع الحسابات؛ ما يلي مقترح غير منفذ:

| العملية | المسار | التفويض والنتيجة |
|---|---|---|
| بحث | GET /v1/lines | نقاط صالحة وفلاتر؛ بيانات خطوط منشورة فقط دون هاتف أو وثائق |
| نشر/تعديل خط | POST /v1/driver/lines، PATCH /v1/driver/lines/:id | سائق موافق عليه ومالك؛ تحقق السعة والجدول والمسار |
| طلب | POST /v1/booking-requests | راكب مسجل؛ نوع daily/monthly وفترة/رحلات؛ Idempotency-Key |
| طلباتي | GET /v1/me/bookings | حجوزات الجلسة فقط |
| طلبات الخط | GET /v1/driver/booking-requests | طلبات خطوط السائق فقط |
| قرار | POST /v1/driver/booking-requests/:id/decision | accept/reject؛ معاملة سعة؛ 409 عند نفاد المقاعد أو تعارض الحالة |
| إلغاء | POST /v1/bookings/:id/cancel | صاحب الحجز أو سائق الخط وفق سياسة معتمدة؛ سجل السبب |
| إثبات كاش | POST /v1/driver/cash-records | المالك فقط؛ لا تحويل unpaid إلى received من جهاز الراكب |

استجابات أخطاء موحدة: code وmessage وrequestId دون بيانات شخصية أو stack. 401 لجلسة غير صالحة، 403 لعدم الصلاحية، 409 للتعارض، 422 لمدخلات غير صالحة، 429 للتجاوز. UUID من العميل لا يمنح صلاحية. يُحدد حد المسافة ومطابقة المسار باختبارات؛ فرز المسافة المباشرة ليس وقت قيادة.

## الاستضافة والتكلفة

التوصية التقنية: استضافة مُدارة لـNode.js مع PostgreSQL مُدار في منطقة مناسبة بعد قياس الاتصال من العراق، وتخزين وثائق خاص ونسخ احتياطية. لا نختار مزودًا تجاريًا نهائيًا دون التحقق من الفوترة والدعم وشروط البيانات والتسليم للعراق. VPS بديل أقل تكلفة محتملة لكنه يحتاج مسؤول تحديثات وأمن ونسخ واستعادة؛ ليس اختياري الأول دون مسؤول تشغيل.

هذه مخصصات تخطيط بالدولار شهريًا، وليست أسعار مزودين متحققة أو عرض شراء:

| البند | مخصص أولي |
|---|---:|
| خدمة API صغيرة | 10–25 |
| PostgreSQL مُدار | 15–35 |
| تخزين وثائق ونسخ احتياطية | 5–15 |
| مراقبة وسجلات محدودة | 0–10 |
| المجموع الثابت التقريبي | 30–85 |

تضاف: النطاق والضرائب ونقل البيانات الزائد وSMS والخرائط والعمل البشري والتطوير وحسابات المتاجر. عدد محاولات SMS المحاسبة × سعر المحاولة الفعلي + رسوم المزود. مثال حسابي فقط: 1000 محاولة × 0.08 دولار = 80 دولارًا، فيصبح المثال 110–165 دولارًا قبل الاستثناءات؛ 0.08 ليس سعرًا مثبتًا للعراق. مزود OTP يجب أن يثبت التسليم فعليًا على Zain وAsiacell وKorek، وحدود الإرسال ومكافحة إساءة الاستخدام وسقف الإنفاق.

OSM بيانات مفتوحة، لكن بلاطات الخريطة العامة ليست وعد استضافة مجانيًا غير محدود؛ تُراجع سياسة الاستخدام وحجم التجربة قبل الإطلاق. الدفع الإلكتروني خارج الميزانية الأولى، ولا اشتراك مدفوع أو مورد تم إنشاؤه الآن.

## ترتيب التنفيذ ومعايير الخروج

| الدفعة | التنفيذ | معيار القبول |
|---|---|---|
| 1 — استعادة الحسابات | دمج انتقائي للوحدة الموجودة، migrations واختبارات وCI ووضع تجريبي منفصل | تثبيت نظيف، اختبارات API ومتصفح ناجحة، لا كسر للمحافظات/التتبع/RTL |
| 2 — بيانات الخط والمقاعد | خطوط ورحلات واشتراكات وقرارات السائق والكاش | التزامن على PostgreSQL؛ آخر مقعد يحصل عليه طلب واحد؛ منع الوصول لحساب آخر |
| 3 — ربط الواجهات | التسجيل والبحث وطلبات الراكب وقبول السائق من الشاشات الحالية | الرحلة الكاملة في سياقي متصفح منفصلين ثم هاتفين؛ البيانات تبقى بعد إعادة تشغيل الخادم |
| 4 — بيئة اختبار منشورة | HTTPS وأسرار وDB خاصة ونسخ واستعادة وSMS مناسب | اختبار تسليم فعلي محدود بعد اعتماد التكلفة؛ لا رموز اختبار أو واجهات مشغّل عامة |
| 5 — قبول التجربة | جامعة واحدة، مسؤول مراجعة ودعم، سياسة إلغاء وخصوصية | قبول المالك ونجاح التحقق الميداني واختبارات الأجهزة قبل استقبال العملاء |

تقدير أولي للحسابات والحجوزات فقط: 3–5 أسابيع عمل لمطور متفرغ بعد توفير الخدمات والقرارات؛ ليس موعد تسليم ملزمًا، ولا يشمل شهر التحقق أو مراجعات المتاجر. التتبع الحقيقي والتقييم الأساسي يتبعان ذلك ضمن MVP المنصوص عليه؛ لا يعلن اكتمال MVP بمجرد إكمال الحجز. الدفع الإلكتروني والدردشة والمخالفات المتقدمة لاحقًا وفق PROMPT.

## اختبارات القبول المطلوبة

- OTP خاطئ/منتهٍ/مستهلك، تزامن تحقق الرمز، إعادة الإرسال، فشل المزود، حد الإنفاق؛ لا أكواد في السجلات.
- حساب واحد للهاتف، دخول ثانٍ يعيد الحساب نفسه، خروج يبطل الجلسة، منع CSRF والتلاعب بالدور.
- سائق pending/rejected لا ينشر؛ لا قراءة وثيقة الغير؛ مراجعة بشرية مسجلة لا قبول ذاتي.
- طلبان يتنافسان على آخر مقعد، إلغاء متكرر، موافقة متكررة، فقد الشبكة بعد commit، تكرار المفتاح نفسه مع جسم مختلف.
- اشتراك شهري يتعارض مع رحلة واحدة، تكرار حجز يومي، تقليل سعة دون عدد المؤكدين، حدود التاريخ بتوقيت بغداد.
- الراكب يرى طلبه pending ثم confirmed بعد قرار السائق من جهاز آخر، دون تعديل localStorage.
- إعادة تشغيل الخادم، واستعادة نسخة احتياطية في بيئة معزولة مع تحقق الجداول والوثائق؛ الملفات لا تدخل www أو Git.
- اختبار Android وiOS فعليًا للجلسة والشبكة والأذونات؛ لا اعتبار نجاح المتصفح دليل جاهزية المتاجر.

## قرارات لازمة قبل الإطلاق

اسم الجامعة والخط والسائقين ونتيجة الـ50 مشتركًا؛ مسؤول فحص الوثائق والدعم؛ أيام الاشتراك ومهلة قبول الطلب وسياسة الإلغاء والعطل؛ مزود SMS وعروضه؛ ميزانية شهرية وحد إنفاق؛ الاستضافة ومنطقة البيانات والاحتفاظ والحذف واسترداد الحساب. لا تُطلب مفاتيح أو وثائق شخصية في المحادثة؛ تحفظ الأسرار بإعدادات البيئة فقط.

## دليل المراجعة وحدودها

في 15 تشرين الأول: نجح web:pack واختبارات Node الستة على 0f4b763، بما فيها وجود التسجيل وصحة المسارات وصياغة السكربتات. قبل جلب آخر main ظهر فشل نسخ التسجيل؛ التحديث الموجود أصلحه وأعيد الاختبار بنجاح. تقارير اختبارات فرع الحسابات سابقة وليست إعادة اختبار له اليوم. لم يُختبر PostgreSQL خارجي أو SMS حي أو جهازا هاتف أو استعادة إنتاجية ضمن مراجعة الخطة. لم تتغير شاشات أو ملفات منطق التطبيق، ولم تُنشأ قاعدة إنتاجية أو خدمة مدفوعة.
