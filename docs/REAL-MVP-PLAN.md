# خطة تحويل خَطّي إلى MVP حقيقي

تاريخ الوثيقة: 14 تشرين الأول 2026 — الحالة: **خطة MVP؛ نُفذت وحدة التسجيل في بيئة تطوير فقط**.

تحديث التنفيذ: انظر [دليل التسجيل الخادمي](SERVER-REGISTRATION.md). بقية الخطة، وSMS الفعلية والاستضافة والإنتاج، غير منفّذة. وصف الحالة الأصلية والقرارات أدناه يمثل خط الأساس للخطة ولا يعني اكتمال بوابات الإطلاق.

المرجع الملزم هو [`PROMPT.md`](../PROMPT.md)، خصوصًا الأقسام 3.12 و5 و6. هذه الوثيقة تفصل طريقة التنفيذ المقترحة ولا تغيّر المتطلبات أو تثبت نجاح التحقق الميداني. حالة النموذج السابق موثقة في [`PHASE1-REPORT.md`](PHASE1-REPORT.md).

## 1. الهدف وحدود هذه المهمة

الهدف الأول: حساب راكب يبقى محفوظًا عند تغيير الجهاز، وسائق لا ينشر قبل مراجعة بشرية، وحجز مؤكد لا يتجاوز سعة المركبة. تُربط الواجهات الحالية بالخدمات تدريجيًا مع الحفاظ على العربية وRTL والألوان والتصميم.

لم تُنشأ قاعدة بيانات إنتاجية أو حسابات مزودين أو اشتراكات مدفوعة ولم يبدأ استقبال بيانات عملاء. أضيف خادم تطوير يحفظ حسابات اختبار ويمنع القبول الذاتي؛ العرض الثابت على GitHub Pages ما زال يستخدم `localStorage`. الرموز SMS والحجز والتتبع لم تصبح خدمات إنتاجية.

### بوابة الانتقال

وفق قسم 6، يسبق البناء الحقيقي تحقق لمدة شهر: خط واحد، 2–3 سائقين، حجوزات عبر واتساب وجدول، والهدف 50 مشتركًا دافعًا. يوثق المالك المدفوعات والاستردادات والاستمرار ومشكلات التشغيل قبل اعتماد ميزانية التنفيذ. لا توجد في المحادثة نتيجة ميدانية مؤكدة؛ إعداد الخطة لا يعني تجاوز هذه البوابة.

### نطاق الإصدار الأول بعد الاعتماد

| يدخل MVP لجامعة واحدة | يؤجل وفق ترتيب المرجع |
|---|---|
| تسجيل راكب وتوثيق سائق، بحث وفلترة وصفة خط، حجز يومي/شهري وكاش | منظومة المخالفات المتكاملة ثم الدردشة ثم خريطة الطلب ثم الدفع المسبق |
| تتبع أثناء نافذة الرحلة، مشاركة أهل بموافقة الراكب، تنبيهات أساسية | رحلات العطل والمطابقة والتقارير الموسعة والتعليقات الكاملة ضمن إصدارات لاحقة |
| تقييم أساسي متبادل وفق شروط التقييم الأعمى | رصد المخالفات الآلي والعقوبات والتكاملات الموسعة |

تظل الشاشات الحالية محفوظة. في النسخة الحقيقية تُعطّل إجراءات الميزات غير المربوطة أو توضح أنها غير متاحة؛ لا تُخلط معاملات حقيقية ومحاكاة في الرحلة نفسها. لا واجهة مؤسسات، ولا طرف تجاري ثالث، ولا تغيير لنطاق المشروع. أداة مراجعة السائقين الداخلية للمشغّل تخدم التوثيق المطلوب ولا تمثل واجهة جامعة أو شركة.

## 2. المعمارية المقترحة

قرار مقترح قابل للمراجعة: خادم واحد منظم إلى وحدات، بدل خدمات مستقلة متعددة في البداية.

| الجزء | الاختيار المقترح | الغرض |
|---|---|---|
| الواجهات | HTML/CSS/JavaScript الحالية + Capacitor | الحفاظ على الشاشات وإضافة طبقة اتصال مشتركة |
| الخادم | Node.js LTS مدعوم، TypeScript وFastify | API والتحقق والصلاحيات وقواعد التشغيل |
| البيانات | PostgreSQL؛ PostGIS عند تنفيذ بحث المسافة | معاملات السعة والاشتراكات والبحث المكاني |
| الوثائق | تخزين كائنات خاص متوافق مع S3 | صور الإجازات بروابط مؤقتة وصلاحيات محددة |
| أعمال الخلفية | مهام مجدولة وجدول outbox في PostgreSQL | الحذف المؤقت، التنبيهات وإعادة المحاولة دون فقد الأحداث |
| تحقق الهاتف | مزود SMS يثبت عمليًا دعمه لأرقام العراق | OTP حقيقي؛ لا اختيار أو شراء قبل تجربة التسليم |
| الخرائط | Leaflet وOpenStreetMap | الحفاظ على الخرائط؛ تقييم مزود بلاطات يناسب حجم التشغيل وشروطه |
| الإشعارات | موصل إشعارات موبايل/ويب عند الحاجة | ربط الأحداث بعد نجاح حفظها؛ لا يُوصف قبول المزود بأنه وصول مؤكد |

يبقى GitHub Pages مناسبًا لملفات الويب الثابتة فقط؛ لا يشغّل API ولا يخزن سجلات العملاء. يستضاف الخادم وقاعدة البيانات بشكل مستقل عبر HTTPS، وتُحدد أصول CORS المسموحة بدقة. تختبر أصول Capacitor فعليًا بدل السماح لكل الأصول.

توجد بيئات منفصلة: تطوير ببيانات اصطناعية، واختبار قبول، وإنتاج بعد الاعتماد. لا تدخل بيانات الإنتاج أو أسرارها إلى المستودع أو سجلات CI. لا حاجة إلى Redis أو خدمات مدفوعة إضافية دون سبب مقاس.

## 3. التسجيل والجلسات وحفظ بيانات العملاء

### تدفق الراكب

1. إدخال الاسم والهاتف، وتوحيد الهاتف إلى صيغة `+964` والتحقق من أرقام المحمول المدعومة، بما فيها الإدخال بالأرقام العربية. لا يُعتمد تحقق الواجهة وحده.
2. طلب تحدي OTP من الخادم؛ يطبق حدًا للهاتف وعنوان الشبكة والجهاز وضبط إنفاق، ويرد برسالة لا تكشف وجود الحساب.
3. إرسال الرمز عبر مزود فعلي. اقتراح أولي: صلاحية 5 دقائق، 5 محاولات كحد أقصى، وفاصل إعادة إرسال 60 ثانية؛ تضبط هذه الحدود بعد تجربة الاستخدام وتوافق المزود.
4. التحقق في الخادم واستهلاك التحدي مرة واحدة. لا يحفظ الرمز نصًا صريحًا ولا يسجل في logs؛ يستخدم HMAC بمفتاح خادمي أو التحقق المُدار لدى المزود.
5. إنشاء الحساب/تسجيل دخوله وتسجيل موافقة الخصوصية وإصدار جلسة. لا يُنشأ حساب نشط لمجرد نجاح طلب إرسال SMS.
6. حفظ الاسم والهاتف والدور في PostgreSQL. يعيد `GET /v1/me` الحساب نفسه بعد الدخول من جهاز آخر.

تغيير الهاتف يتطلب تحققًا من الرقم الجديد وإجراء حماية للحساب، وليس تعديلًا محليًا. فقدان الرقم واسترداد الحساب يحتاجان إجراء دعم يعتمد قبل الإنتاج؛ لا يقبل تغيير الهاتف بناء على الاسم فقط. يجب معالجة خطر تبديل شريحة SIM؛ OTP يثبت التحكم الحالي بالرقم ولا يثبت الهوية المدنية.

### تدفق السائق

بعد تحقق الهاتف، يسجل السائق المركبة ويختار صورة الإجازة. يمنح الخادم إذن رفع قصير العمر لمفتاح ملف مولد خادميًا. يفحص الحجم والنوع الفعلي ومحتوى الصورة، ويعزل الملفات حتى الفحص ويزيل البيانات الوصفية غير اللازمة. لا يكفي امتداد الملف أو MIME الذي يرسله المتصفح.

تُحفظ بيانات السائق بحالة `pending_review`، والملف في مخزن خاص. يقوم مراجع مخوّل بقبول الطلب أو رفضه مع سبب وتاريخ وهوية المراجع. قرار القبول يسجل في سجل تدقيق. لا يستطيع السائق تغيير حالة التوثيق أو منح نفسه شارة الثقة عبر API. القبول لا يمنح شارة «موثوق» تلقائيًا؛ تلزم أيضًا شروط التقييم والمخالفات في المرجع.

### الجلسات والخروج

- الويب: جلسة عبر cookie بـ `HttpOnly` و`Secure` وسياسة `SameSite` مناسبة لطريقة النشر، مع حماية CSRF وفحص الأصل للعمليات المغيرة للبيانات.
- الموبايل: رموز وصول قصيرة العمر، وتجديد دوّار قابل للإبطال محفوظ في Keychain/Keystore عبر مكوّن مدقق. لا تحفظ رموز الجلسة في `localStorage`.
- تسجيل الخروج يبطل الجلسة ويزيل نسختها المحلية **ولا يحذف حساب العميل**. إلغاء الجلسات الأخرى وحذف الحساب عمليتان منفصلتان.
- قاعدة البيانات هي المصدر المرجعي. cache محلي محدود لاحتياجات ضعف الاتصال، دون الوثائق أو الرموز أو أرشيف مواقع. لا تسمح حالة محلية بتجاوز قرار الخادم.
- لا تُرحّل بيانات `khatti_demo_v1_*` إلى الإنتاج باعتبارها حسابات أو حجوزات؛ يعاد التسجيل والتحقق الحقيقيان.

## 4. نموذج البيانات الأولي

هذا مخطط منطقي للمراجعة، وليس migrations منفّذة. المعرفات UUID، والتواريخ المخزنة UTC مع العرض والجدولة بمنطقة `Asia/Baghdad`. المبالغ أعداد صحيحة مع العملة `IQD`، وليست أرقام فاصلة عائمة.

| الكيان | أهم الحقول والعلاقات | القيد الأساسي |
|---|---|---|
| `users` | id، full_name، phone_e164، phone_verified_at، status، created_at | الهاتف فريد للحساب النشط؛ لا يعاد استعمال رقم محذوف قبل سياسة معتمدة |
| `user_roles` | user_id، passenger/driver | لا يمكن طلب دور مراجع من التسجيل العام؛ لا هاتف معلن في النتائج |
| `auth_challenges` | destination، purpose، code_digest/provider_ref، expires_at، attempts، consumed_at | تحدٍ محدود العمر والمحاولات والاستخدام |
| `sessions` | user_id، token_digest، device، expires_at، revoked_at | لا رموز خام في قاعدة البيانات أو السجلات |
| `driver_profiles` | user_id، review_status، reviewed_by، reviewed_at، rejection_reason | التعديل على قرار التوثيق للمراجع فقط |
| `vehicles` | driver_id، type، plate، year، seat_capacity | سعة صحيحة موجبة وحدود معقولة؛ التغيير لا يلغي حجوزات قائمة ضمنيًا |
| `driver_documents` | driver_id، object_key، content_type، size، scan_status، retention_until | ملفات خاصة؛ لا رابط عام دائم |
| `lines` | driver_id، vehicle_id، governorate، area، destination، composition، price_day/month، status | لا نشر قبل قبول السائق؛ لا تعديل خط سائق آخر |
| `pickup_points` / `line_schedules` | line_id، coordinates، ترتيب، أيام وأوقات الذهاب والإياب | إحداثيات صحيحة؛ قواعد زمنية واضحة |
| `trip_instances` | line_id، service_date، direction، departure_at، arrival_at، capacity، state | نسخة رحلة محددة؛ نسخة سعة ومسار لا تتغير بلا معالجة الحجوزات |
| `subscriptions` | passenger_id، line_id، start/end، days/directions، status | اشتراك شهري لا يعني حجزًا غير محدود أو غير محدد الأيام |
| `bookings` | passenger_id، trip_id، subscription_id اختياري، seats، state، idempotency_key | منع تكرار الحجز النشط لنفس الراكب/الرحلة ومعاملة ذرية للسعة |
| `cash_records` | booking/subscription_id، amount، currency، recorded_by، recorded_at | تسجيل تحصيل كاش ليس تحويلًا ماليًا ولا تأكيد بوابة دفع |
| `guardian_links` / `guardian_grants` | رابط ذو token_digest، أبناء مرتبطون، passenger_consent_at، revoked_at | موافقة لكل راكب؛ إمكانية إلغاء ابن أو تدوير الرابط؛ لا دور تجاري ثالث |
| `trip_locations_current` | trip_id، position، recorded_at، received_at، sequence، expires_at | آخر موقع صالح فقط، بلا أرشيف تحركات دائم |
| `ratings` | trip_id، author_id، target_id، score، tags، submitted_at، reveal_at | تقييم واحد لكل طرف خلال 48 ساعة؛ الكشف وفق قواعد العزل الأعمى |
| `notification_outbox` | event_id، destination_ref، status، attempts، next_attempt_at | لا فقد للأحداث بعد commit ولا إرسال مكرر لنفس الحدث |
| `audit_events` | actor_id، action، entity_id، time، safe_metadata | لا نسخ للوثائق أو OTP أو إحداثيات مستمرة في سجل التدقيق |

جدول المراجعين الداخلي وصلاحياتهم منفصل عن الأدوار العامة. مخطط المخالفات والدردشة والمدفوعات الإلكترونية يُفصل عند الوصول إلى مرحلته؛ لا تبنى جداول إنتاجية بلا تدفق معتمد لمجرد توقع الحاجة.

### السعة والاشتراك الشهري

الحجز اليومي يشير إلى رحلة واتجاه وتاريخ محددين. الاشتراك الشهري يحدد بداية ونهاية وأيام الخدمة والاتجاهات ويولد حجوزات الرحلات المشمولة داخل معاملة. العرض الشهري في الواجهة يتطلب اعتماد سياسة هذه الأيام قبل التنفيذ؛ لا يُفسر الاشتراك تلقائيًا بأنه جميع الأيام.

تُقفل الرحلة داخل معاملة PostgreSQL ثم تجمع المقاعد المحجوزة الفعالة، وتُرفض الزيادة قبل الإدراج. عند اشتراك يشمل عدة رحلات تُقفل الرحلات بترتيب ثابت لمنع deadlocks؛ إما ينجح الاشتراك كاملًا أو يعاد رد يشرح تعارض الأيام دون خصم سعة جزئي. تقيد تعديلات السعة بما يحافظ على الحجوزات القائمة. يستخدم مفتاح idempotency مرتبط بالمستخدم والعملية وبصمة الطلب لإعادة نفس النتيجة عند انقطاع الشبكة، ويرفض استعمال المفتاح مع جسم مختلف.

الإلغاء يحرر السعة مرة واحدة مع سجل الحالة. تعتمد مهلة الإلغاء وتعديل الجدول واسترداد النقد قبل إطلاق الحجز الحقيقي؛ لا تُخترع غرامة أو سياسة استرداد أثناء التنفيذ.

## 5. مصفوفة الصلاحيات

| العملية | راكب | سائق | حامل رابط الأهل | مراجع داخلي |
|---|---|---|---|---|
| البيانات الشخصية | حسابه فقط | حسابه فقط | لا بيانات حسابات | الحد الأدنى اللازم للمهمة وبسجل تدقيق |
| البحث عن الخطوط | بعد التسجيل | عرض الخطوط المسموح بها | لا | بحسب مهمة الدعم |
| إنشاء/إلغاء حجز | حجوزه وفق السياسة | لا حجز باسم راكب بلا تفويض | لا في MVP | معالجة دعم موثقة وفق السياسة |
| نشر/تعديل خط | لا | خطه فقط وبعد قبول التوثيق | لا | لا انتحال للسائق؛ تدخل دعم مصرح ومدقق فقط |
| قراءة وثيقة إجازة | لا | وثيقته فقط | لا | مراجع موكّل بالطلب فقط |
| قبول التوثيق | لا | لا | لا | نعم، بمصادقة قوية وتسجيل القرار |
| إرسال الموقع | لا | رحلة خطه أثناء النافذة | لا | لا |
| مشاهدة الموقع | رحلة حجزه المسموح | رحلته | الأبناء الموافقون أثناء النافذة فقط | لا وصول افتراضي للمواقع |
| تقييم | طرف رحلته المكتملة | طرف رحلته المكتملة | لا | لا إنشاء تقييمات باسم المستخدم |

كل قرار ينفذ في الخادم لكل طلب ولكل معرف. UUID أو إخفاء الزر أو `verified` محلي لا يمثل حماية. رابط الأهل سر وصول: token عشوائي قوي، يخزن ملخصه، لا يظهر في logs/analytics، ويمنع التخزين المؤقت وتسريب Referer. لا يتيح الهاتف أو الوثائق أو تاريخ الحركة. تعطى استجابة عامة للرابط غير الصالح دون كشف وجود الابن.

## 6. عقود API الأولية

| المسار | الغرض | شرط القبول |
|---|---|---|
| `POST /v1/auth/otp/request` | بدء تحدي الهاتف | ضبط المعدل والإنفاق، لا حساب نشط ولا كشف وجوده |
| `POST /v1/auth/otp/verify` | تحقق وإصدار جلسة | تحدٍ صحيح لم ينته ولم يستهلك |
| `POST /v1/auth/logout` | إبطال الجلسة | لا حذف للحساب |
| `GET /v1/me`، `PATCH /v1/me` | قراءة وتعديل الحساب | whitelist للحقول؛ لا تغيير verified/role/phone مباشرة |
| `POST /v1/driver/document-uploads` | إذن رفع خاص | مستخدم مخوّل، حجم ونوع محددان |
| `POST /v1/driver/submissions` | طلب مراجعة | اكتمال البيانات ونجاح فحص الوثيقة |
| `POST /v1/internal/driver-reviews/:id/decision` | قرار بشري | مراجع مخوّل؛ لا يصل إليه تطبيق الجمهور |
| `GET /v1/lines` | بحث وفلترة وpagination | لا أرقام هاتف؛ المسافة أولًا عند وجود الدبوس ثم الثقة والتقييم عند التعادل |
| `POST /v1/lines`، `PATCH /v1/lines/:id` | إدارة الخط | ملكية الخط وقبول السائق؛ تنبيه تغيّر الصفة |
| `POST /v1/bookings`، `POST /v1/subscriptions` | حجز حقيقي | جلسة، سعة، idempotency، سياسة شهرية معتمدة |
| `GET /v1/me/bookings`، `POST /v1/bookings/:id/cancel` | متابعة/إلغاء | ملكية وسجل حالة ومعاملة لتحرير المقعد |
| `POST /v1/trips/:id/locations` | تحديث GPS | سائق الرحلة، نافذة مفتوحة، وقت وإحداثيات وتسلسل صالح |
| `GET /v1/trips/:id/location` | موقع الرحلة الحالي | راكب مخوّل؛ لا إرجاع موقع قديم بعد انتهاء النافذة |
| `POST /v1/guardian-links`، `DELETE /v1/guardian-links/:id` | مشاركة وإلغاء | موافقة الراكب على الأبناء المحددين |
| `GET /v1/guardian/trips` | عرض الرابط الثابت | token صالح، موافقة سارية ونافذة رحلة |
| `POST /v1/trips/:id/ratings` | تقييم أساسي | طرف رحلة مكتملة، 48 ساعة، مرة واحدة؛ كشف متبادل فقط بعد تقييم الطرفين |

ترد الأخطاء ببنية ثابتة مثل `error.code` و`message` و`request_id`، دون stack trace أو بيانات شخصية. رموز متوقعة: 400 مدخلات، 401 جلسة، 403 صلاحية، 404 عنصر غير متاح، 409 سعة/تعارض، 429 حد الطلبات، 503 عطل مؤقت. تعرض الواجهة «لم يكتمل الطلب» عند الفشل، وتراجع الحالة بمفتاح العملية قبل إعادة حجز محتمل. لا تعتبر timeout نجاحًا أو فشلًا ماليًا مؤكدًا.

## 7. التتبع والخصوصية والتشغيل

- تحديث كل 10–15 ثانية خلال نافذة الرحلة فقط. البداية قبل الموعد بساعة؛ مدة السماح بعد الوصول تحتاج رقمًا معتمدًا من المالك قبل التنفيذ.
- يقرر الخادم النافذة من جدول الرحلة وحالتها؛ لا يعتمد على ساعة الجهاز فقط. يرفض نقاطًا قديمة أو خارج النافذة، ويحذف آخر موقع عند الإغلاق ويمنع قراءته فورًا.
- طابور النقاط دون اتصال مؤقت ومحدود ومشفر حيث يتاح؛ لا يرفع نقاط رحلة انتهت، ولا يحتفظ بمسار تاريخي. بعد الاستلام تُحدّث أحدث نقطة فقط وتزال النقاط المحلية المرسلة. لا يحول الرصد الآلي المؤجل هذا المخزن إلى أرشيف دائم.
- تعرض قدم الموقع وانقطاع الاتصال؛ لا تتحرك علامة الباص بالمحاكاة في وضع حقيقي. وقت الوصول تقدير يحتاج اختبارًا ولا يمثل وعدًا.
- تنبيهات الصعود والوصول تستند إلى حدث رحلة موثوق أو تأكيد محدد، لا إلى مؤقت وهمي. التنبيه لا يعوض خدمة الطوارئ.
- تعتمد قبل الإنتاج سياسة حذف للحساب والوثائق والحجوزات وموافقات الأهل والنسخ الاحتياطية، وفترات زمنية مكتوبة ومسؤول تنفيذ. لا تحدد هذه الخطة فترة قانونية باعتبارها حقيقة عراقية دون مراجعة مختصة.
- لا تسجل مواقع الرحلة في logs أو analytics أو audit ولا تُدرجها في نسخ تاريخية؛ يفصل مخزن الموقع القصير العمر عن النسخ الاحتياطية الدائمة. يختبر ألا تعيد الاستعادة مواقع منتهية أو روابط ملغاة.
- نسخ احتياطي مشفر للحسابات والحجوزات مع تجربة استعادة. هدف أولي للمراجعة: RPO حتى 24 ساعة وRTO حتى 4 ساعات؛ لا وعد للعميل قبل قياسه واعتماده.
- مراقبة أعطال API وفشل SMS وحجم التخزين والسعة وتنبيهات الميزانية؛ تنقيح الهواتف والوثائق والرموز من التقارير. سياسة خصوصية وموافقة مناسبة لربط الأبناء قبل جمع بيانات حقيقية.

## 8. الخدمات والتكلفة المتوقعة

الأرقام أدناه **مخصصات تخطيطية بالدولار وليست أسعار مزودين متحققًا منها أو عروض شراء**. لا اختيار لمزود نهائي ولا ضمان خطة مجانية. تُطلب عروض حديثة ودعم فعلي للعراق وشروط احتفاظ وموقع استضافة قبل التعاقد. لا تعتمد رسوم SMS على تقدير عالمي فقط.

افتراض المثال: 50–100 مستخدم نشط، 2–3 سائقين، جامعة واحدة، 1,000 محاولة إرسال OTP شهريًا، واستخدام صور محدود. يفصل عدد محاولات الإرسال عن عدد المسجلين لأن إعادة المحاولة والاحتيال قد ترفع الإنفاق.

| البند | مخصص تخطيطي | ما يجب التحقق منه |
|---|---|---|
| خادم API صغير | 10–25 دولار/شهر | السعة والمراقبة والنقل وبيئة الاختبار |
| PostgreSQL مُدار ونسخ احتياطي | 15–35 دولار/شهر | وجود النسخ والاستعادة وحدود التخزين ضمن العرض |
| ملفات خاصة ونقلها | 1–5 دولارات/شهر | التكلفة الدنيا ورسوم النقل والفحص |
| مراقبة وسجلات منقحة | 0–10 دولارات/شهر | حدود الخطة وفترة الاحتفاظ |
| نطاق وTLS | نطاق تقريبي 10–25 دولار/سنة؛ TLS قد يكون بلا رسم منفصل | السعر الفعلي والتجديد وخدمة الإصدار |
| SMS إلى العراق | السعر الفعلي مطلوب | شبكات الاتصال، اسم المرسل، الرسائل الفاشلة، رسوم التحقق والتأسيس |
| بلاطات الخرائط | عرض يناسب الحجم، غير محسوب أدناه | لا يُفترض أن خادم OSM العام مجاني بلا حدود أو SLA |
| المراجعة والدعم | وقت بشري، غير محسوب أدناه | من يراجع ومتى وكيف تعالج الشكاوى والانقطاع |

المجموع الثابت التوضيحي للبنود الأربعة الأولى: **26–75 دولارًا شهريًا**، قبل SMS والخرائط والنطاق والضرائب والتطوير والدعم والأجهزة ورسوم المتاجر. إذا كان عرض SMS مثلًا 0.08 دولار للمحاولة المحاسبة، فإن 1,000 محاولة = 80 دولارًا، فيصبح المثال 106–155 دولارًا قبل الاستثناءات؛ **0.08 فرض حسابي لا سعر موصى به أو مثبت للعراق**.

معادلة الميزانية: استضافة + قاعدة + تخزين/نقل + مراقبة + عدد محاولات SMS المحاسبة × السعر الفعلي + رسوم المزود الثابتة + الخرائط + الدعم. يضبط حد إنفاق وتنبيهات قبل إتاحة OTP للعامة. لا مفاتيح مزودين في التطبيق أو GitHub؛ تدخل القيم عبر إعدادات الأسرار المعتمدة عند اختيار الخدمة.

الدفع الإلكتروني خارج ميزانية MVP الأولى. ربط Zain Cash/آسيا حوالة لاحقًا يتطلب اتفاق تاجر ووثائق تكامل وبيئة اختبار وتسوية واسترداد ورسوم فعلية. لا PayPal أو Stripe ولا اعتماد رسالة العميل دليلًا على الدفع. لا تظهر «تم الدفع» إلا بعد تأكيد خادمي موثق من المزود في تلك المرحلة.

## 9. مراحل التنفيذ ومعايير القبول

| المرحلة | المخرج | معيار الخروج |
|---|---|---|
| A — اعتماد النطاق | نتيجة التحقق الميداني، سياسة التشغيل والخصوصية، عروض الخدمات | توثيق موافقة المالك والميزانية؛ تعيين مسؤول المراجعة |
| B — التسجيل الحقيقي | API وقاعدة اختبار ومزود OTP تجريبي/فعلي وتخزين وثائق خاص | جميع اختبارات التسجيل أدناه؛ لا بيانات عملاء قبل النجاح |
| C — البحث والحجز والكاش | خطوط جامعة واحدة ورحلات واشتراكات وسعة ذرية | اختبار تزامن حجز آخر مقعد واختبار الاسترداد من نسخة احتياطية |
| D — التتبع والأهل | GPS حقيقي محدود بالنافذة وموافقة وإلغاء وتنبيهات أساسية | اختبار هاتفين وصلاحيات خارج النافذة وضعف الإنترنت وقدم الموقع |
| E — التقييم والتجربة | تقييم أساسي أعمى ونسخ ويب/Android/iOS | 48 ساعة، منع التكرار والتسريب، اختبار أجهزة وقبول ميداني محدود |

ترتيب B يبدأ بالحسابات في بيئة اختبار، ولا يعني إطلاق التسجيل العام قبل تكامل بقية MVP. يمكن تقييم نتائج كل مرحلة دون إعادة بناء الواجهة. التقدير الأولي للعمل الكامل 6–10 أسابيع لمطوّر متفرغ متمرس بعد توافر القرارات والخدمات وأجهزة الاختبار؛ ليس التزام تسليم، ولا يشمل التحقق الميداني أو تأخير الموردين أو مراجعات المتاجر. يُراجع التقدير بعد تثبيت عقود البيانات والخدمات.

### اختبارات قبول التسجيل وحفظ العملاء

1. الهاتف والاسم غير الصالحين يُرفضان خادميًا، مع دعم الصيغة العراقية المتفق عليها والأرقام العربية.
2. الرمز الخاطئ والمنتهي والمستهلك لا ينشئ جلسة؛ تجربة الحدود وإعادة الإرسال وانقطاع المزود، دون تسجيل OTP.
3. التسجيل المتزامن بالهاتف نفسه لا ينشئ حسابين؛ تسجيل الدخول يعيد الحساب القائم دون كشف وجوده في استجابة طلب الرمز.
4. الدخول من جهاز ثانٍ يعرض البيانات المحفوظة نفسها من الخادم. مسح cache لا يحذف الحساب؛ الخروج يبطل الجلسة ولا يحذف السجل.
5. لا يمكن قراءة أو تعديل ملف عميل آخر بتغيير id، ولا نشر خط بإرسال `verified:true` أو `role:reviewer`.
6. لا يستطيع السائق قراءة وثيقة سائق آخر، والروابط المؤقتة تنتهي؛ يرفض الملف المزيف والكبير وتوثق مراجعة الطلب.
7. فشل الحفظ أو SMS لا يعرض تسجيلًا ناجحًا، وإعادة المحاولة لا تكرر الحساب أو الإرسال بلا حدود.
8. إبطال جلسة أو تدوير رمز تجديد يمنع إعادة استخدامها؛ تختبر CORS/CSRF وcookies وتخزين رموز الموبايل.
9. النسخة الاحتياطية تستعاد إلى بيئة معزولة، وتتحقق بيانات الحساب والحجوزات دون إعادة تفعيل جلسات أو روابط أُلغيت بعد النسخة؛ يعاد تطبيق سجل الإبطال/الحذف أو تبطل الجلسات والروابط عند الاستعادة وفق إجراء معتمد.
10. لا يحتفظ وضع الإنتاج بأي OTP تجريبي أو قبول سائق ذاتي أو نسخ تلقائي لعملاء العرض المحلي.

### اختبارات قبول MVP التشغيلية

- طلبان متزامنان لآخر مقعد: حجز واحد ناجح والآخر تعارض؛ لا سعة سالبة، ومعاملة الاشتراك الشهري إما كاملة أو بلا أثر جزئي.
- إعادة طلب الحجز بالمفتاح نفسه تعيد النتيجة ذاتها؛ الإلغاء المتكرر يحرر المقعد مرة واحدة.
- رفض وصول غير المشتركين للموقع، وحجب الأهل فور إلغاء الموافقة أو نهاية النافذة. التحقق من حذف الطابور المنتهي دون أرشيف في النسخ أو logs.
- اختبار التقييم الأعمى قبل تقييم الطرف الثاني وبعده، مع تقييم واحد لكل رحلة وحد 48 ساعة وتقييد عرض تقييم الراكب للسائقين المخولين. لا كشف تلقائي لتقييم أحادي دون قرار متوافق مع المرجع.
- اختبار RTL والخرائط المتعذرة والشبكة الضعيفة على ويب وهاتف Android وiPhone، وتوثيق مخرجات البناء الفعلية بدل الاكتفاء بمزامنة Capacitor.

## 10. القرارات المطلوبة قبل بدء تنفيذ التسجيل

| القرار | المقترح الحالي | حالة الاعتماد |
|---|---|---|
| الجامعة والخط ومسؤول التشغيل | جامعة واحدة وخطوط التحقق الميداني | ينتظر تحديد المالك |
| مزود SMS والاستضافة ومكان البيانات | مقارنة عروض وتسليم فعلي لأرقام عراقية | لم يتم الاختيار أو الشراء |
| المراجع وقواعد قبول السائق | شخص مخوّل وأداة داخلية وصلاحيات محدودة | ينتظر التعيين والسياسة |
| سياسة الاشتراك والإلغاء والاسترداد | أيام واتجاهات وفترة واضحة وكاش أولًا | تحتاج اعتمادًا قبل الحجز |
| مدة ما بعد الوصول وسياسة الاحتفاظ والحذف | أقل مدة لازمة بلا أرشيف حركة | تحتاج مددًا محددة ومراجعة مناسبة |
| ميزانية التجربة | حساب وفق العروض وعدد الرسائل وحد إنفاق | لم تُعتمد |

الخطوة التنفيذية التالية بعد اعتماد هذه الوثيقة ونجاح التحقق الميداني: فرع مستقل لوحدة التسجيل في بيئة اختبار، يبدأ بعقود API وmigrations واختبارات الصلاحيات ثم ربط شاشة التسجيل الحالية. لا يُعلن أن بيانات العملاء محفوظة فعليًا على خادم حتى تنجح اختبارات القبول والاستعادة والتسليم على الأجهزة المطلوبة.
